# POS Session Scope Candidate

Source review of the historical priced-sale command and API session-hash reader found no current employee/assignment/tenant/register status check on sale completion. Catalog context checks some current statuses, but that is not a prerequisite to a direct completion request. This was a source finding, not a live exploit or financial test.

Migration `20261017092126_pos_session_scope_invalidation` protects the shared credential boundary. New active sessions must match an active tenant, employee, employee-location assignment, location, register and device, with matching device/register/location bindings. Changes that invalidate this scope revoke matching unexpired credentials transactionally. Reinstating a scope does not revive old tokens; normal PIN sign-in creates a new credential. Existing unexpired out-of-scope credentials are invalidated during migration. Expired/revoked session history and all financial/inventory/loyalty/audit/outbox truth remain intact. Session credentials are mutable security state, not a commerce ledger.

The private predicate is VOLATILE so invalidation triggers inspect current changed rows, not a cached pre-update snapshot. Tenant scans are bounded by a partial tenant/expiry index, and cross-tenant invalidation takes canonical tenant order. Device status/binding, register status/location, location status, employee status and assignment deletion/update are covered. Invalid normal login scope returns opaque invalid status rather than a credential or HTTP 500. Helpers and the original authentication core are not executable by browser or Hyperdrive roles.

Regression fixture tests an authorized sale, immediate subsequent fresh-sale/completed-replay denial after suspension, unchanged money/stock/audit/outbox/idempotency snapshots, unrelated cashier survival, context/pricing/register-open denial, invalid session creation, removed/reassigned location, inactive location/register/device/tenant, matching device bindings, opaque normal PIN denial and private helper ACLs. In-flight already-authorized transactions are not claimed to be cancelled by a later status change; this is not new multi-session race proof. No shared environment, credential or live transaction was used for development.
