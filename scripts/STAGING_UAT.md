# Controlled Staging UAT Runners

These tools target the fixed HUSTLERO Staging API/Auth project only. They are not application deployment commands. No Production target, browser-session extraction, secret/service-role key or privileged SQL business write is supported.

Run unit regressions with `npm test`. Formatting and lint include `scripts/staging-*.mjs`; complete application/database CI remains mandatory before release. Unit mocks never constitute live UAT evidence.

## Private Local Execution

With the approved Staging publishable key in process environment only, set `HCS_STAGING_UAT_MODE` to exactly one of `isolation`, `fund-recovery`, `paid-replay`, `paid-rollback`, `approval-consumption`, `second-tenant-bootstrap`, `second-tenant-fixtures`, `second-tenant-fixtures-resume`, `cross-tenant-owner`, or `cross-tenant-tester`, then run `node scripts/staging-isolation-server.mjs`.

The runner binds `127.0.0.1:3014`, validates Host/Origin/random nonce, returns no-store/restrictive-CSP headers, and accepts one private password form submission. Credentials stay in process memory and the created harness session is logged out locally after the batch. Clearing references is not a guarantee of cryptographic memory erasure. No new password is generated or saved. Sanitized result is available at `/result`; stop the runner after collecting it.

Exact live side effects/access must be owner-approved before execution. Owner-required modes also require a matching form attestation. Never reuse the restricted tester as an owner, widen its role automatically, transmit credentials to Production or retry a changed command using a new key after an unknown outcome.

## Modes And Limits

- `isolation`: exact temporary non-owner/single-branch/two-permission tester. Assigned report reads, explicit unauthorized Main Store/non-member sentinel tenant and rejected confirmation on a nonexistent order. Deactivate approved temporary access immediately after the batch; session logout alone does not revoke membership.
- `cross-tenant-tester`: same exact PABL0 Branch 2 tester, but twenty checks use real populated B and its reconciled order, not nonexistent sentinels. Only one fixed-key confirmation POST under PABL0 is allowed and must fail authorization; all other requests are enumerated reads. B receivables/payments/statements must deny, allowed reads must exclude known B references, and owner/extra-membership/broadened branch or role stops before commands. B must independently be active/populated inside its approved window. This named candidate is bounded to October 14; no automatic fixture recreation, renewed access, grant or retry. Deactivate tester and suspend B after independent reconciliation.
- `fund-recovery`: one fixed synthetic receipt split into Capital/Operating funds. Exact-key response replay and wrong-split/duplicate denials. The append-only allocation remains; no real settlement or bank transfer is inferred.
- `paid-replay`: fixed historical COD/Prepaid keys/bodies. Returns original invoices even after order cancellation. Changed-body/new-key and approval-creation scope/expiry denials; no fresh delivery planned.
- `paid-rollback`: one fixed fresh mixed-variant draft, temporary COD limit, confirmation, rejected unpaid/under/over/missing-method fulfillment, cancellation and original-term restoration. Unexpected concurrent settings are not overwritten. Cleanup preserves any unexpected business truth rather than deleting it.
- `approval-consumption`: fixed fresh mixed-variant draft pair, exact bounded exceptions, server-observed expiry and isolated order/action denials. Only supported confirmed/partial orders are cancelled; inert drafts remain unfulfilled/unreserved with all test approvals revoked. This cleanup interpretation needs owner acceptance. Per-case progress is retained on failure.
- `second-tenant-bootstrap`: existing owner with one PABL0 membership creates the fixed synthetic business/main location/owner membership only. No financial fixture, entitlement or tester grant. Emits creation identifiers before post-create checks; ambiguous outcomes are not retried. Stop for independent reconciliation and separate platform prerequisites. A passing preparation phase is not a populated cross-tenant matrix pass. Business suspension belongs to the separately authenticated platform cleanup stage, never the owner bootstrap transport.
- `second-tenant-fixtures`: fixed created B business/location only, after independently verified bounded wholesale entitlement. Enables Inventory/Customers/Advanced Wholesale through onboarding, creates one reseller/product/price list/additional synthetic cash method, posts one opening unit, records B-only Net 7/PHP 1 test limit, fulfills one PHP 1 invoice and allocates one PHP 1 receipt. Existing four system payment methods are preserved. Transport disallows PABL0 writes, other quantities/amounts and unbound identifiers; captures PABL0 contexts before/after. Unknown/failed writes stop without a new key or automatic retry. Reconcile partial effects and use the separately authenticated platform to suspend B on failure; no SQL deletion or unapproved financial reversal. Full isolation matrix/tester cleanup/B suspension follow, not implied by fixture success.

Fixed fixture/key modes deliberately fail preflight if already-used orders exist. Do not change fixture names or grant new access to obtain a passing rerun without a separately reviewed/approved plan. The original approval batch failed cleanup; corrected local tooling does not retroactively turn it into a live pass.

## Evidence Rules

`cross-tenant-owner` uses the reconciled populated B manifest for two-business positive reads and fourteen expected foreign-reference denials under selected PABL0. Owner owns both businesses: this does not prove non-member denial. Well-shaped scope failures need exact codes/trace/error-only responses; generic draft validation is not accepted. All bodies/keys/targets are fixed, any unexpected acceptance stops immediately and needs independent reconciliation. No new successful order/payment/fund allocation is intended. Separate restricted tester and platform suspension are mandatory later cleanup/evidence stages.

`second-tenant-fixtures-resume` is explicitly owner-approved for the reconciled October 14 partial setup after renewed B-only access. It opts into exact saved-profile reuse, skips profile mutation and retains original unused financial keys/budget. It does not resume an unknown financial outcome or accept completed/unrelated setup. This is not the default fresh mode and must not be selected without reviewed approval.

Second-tenant fixture correction: active onboarding options are checked before any write, including profile creation. Fresh execution rejects an existing profile; an explicit local-suite resume option accepts only the exact approved saved profile and skips that write, but the runner does not enable this automatically. Renewal/reactivation and resume require reviewed approval after the October 14 expired-window failure. Failure progress retains only status/safe code/UUID trace, not raw error messages. Reconcile partial setup and suspend B instead of blindly restarting.

Verify status and exact error codes, then independently reconcile business counts, balances, reservations, immutable records, audit/outbox uniqueness and rejected idempotency keys. Sanitized console output may retain names/status/error/trace IDs, never raw Auth responses or credentials. Keep private screenshots/CSV/dumps/logs out of the public repository.

Deliberate response discard and historical API replay are not real network-loss/browser-reload proofs. Sentinel tenant denial is not populated second-tenant isolation. Document those limits and unresolved outcomes before separate Production approval.
